# 后端实现方式概览

本文面向项目汇报、联调和后续交接，按功能模块说明“智序知识助手”后端是如何工作的。内容以宏观实现方式为主，不展开到具体代码行。

## 1. 整体架构

后端是一个统一的 FastAPI 服务，对外提供学习资料生成、文件上传、结果读取、契约校验、RAG 查询和继续问答等接口。前端和 Android WebView APK 都通过 HTTP 调用同一套接口，页面只消费归一化后的 `AgentResult`。

整体链路可以理解为：

```text
学习资料输入
  -> 文档解析与分块
  -> 模型 Agent 分阶段生成
  -> RAG 检索与引用 grounding
  -> AgentResult 归一化与校验
  -> 结果持久化
  -> 前端展示、刷新、检索、问答
```

后端内部按职责分层：API 层负责请求入口和错误转换；Service 层负责编排完整流程；Parser/RAG 层负责资料解析、分块、检索和引用；Agent 层负责 M1-M7 模块化生成；Provider 层负责真实模型调用；Contract/Normalization 层负责统一输出结构。

## 2. 输入与解析

后端支持两类输入方式。

第一类是文本输入。前端把用户粘贴的学习资料作为 `sourceText` 提交，后端会把它写入运行目录中的临时 Markdown 文件，再进入统一解析流程。这样文本输入和文件输入后续可以共用同一套解析、分块、生成和引用逻辑。

第二类是文件上传。前端或 APK 通过 multipart 上传 `.txt`、`.md`、`.doc`、`.docx`、`.pdf`、`.pptx` 等资料。后端先把上传文件保存到运行目录，再根据文件类型提取文本。DOCX、PDF、PPTX 会尽量保留页码、段落、幻灯片、标题等定位信息；旧版 DOC 在 Windows 环境中可借助本机 Word 转换为临时 DOCX。

解析后的内容会被组织为结构化 chunk。每个 chunk 会带有来源文件名、chunk id、页码或段落位置、标题、正文和关键词等信息。这些 chunk 是后续生成笔记、召回证据、建立引用回链的基础。

## 3. Hybrid Pipeline

默认主流程是 `hybrid`，也就是“模型生成 + 程序化引用校验”的混合流水线。它不是一次性把资料丢给模型生成所有内容，而是拆成多个 Agent 模块逐步完成。

主要阶段包括：

- M1：解析和清洗输入，确认资料已经被切成可用 chunk。
- M2：生成主题、摘要、关键词、核心知识点和报告式学习结构。
- M3：生成结构化笔记，把资料组织为章节、知识块、要点、例子和关系。
- M4：生成思维导图节点和关系。
- M5：由后端 RAG 程序重新建立引用，不把引用完全交给模型自由编造。
- M6：生成复习题、薄弱点和复习建议。
- M7：作为独立问答接口，基于已保存结果和 chunk 做继续追问。

这种拆分的好处是：每个阶段的输入输出更清楚，模型失败时更容易定位，引用也能在后处理阶段被统一校正。

后端还保留 `rag-only` 流程。它不依赖大模型，主要用于离线解析、RAG 链路测试和契约验证，不作为真实前端生成的兜底 mock。

## 4. RAG 与引用回链

引用可信度是后端的重点能力。生成草稿后，后端会使用 RAG 层重新检索资料 chunk，并把笔记、复习题和来源片段建立可追溯关系。

核心做法是：

- 为每条笔记构造检索 query，综合标题、摘要、要点、结构块和已有 source refs。
- 使用混合检索器从 chunk 中找出最相关的来源片段。
- 为笔记补齐 `citationIds`，让 `notes[].citationIds` 指向真实存在的 `sources[].id`。
- 生成 `citations[]`，记录 note 和 source 的绑定关系、引用片段、定位信息和置信度。
- 校验复习题中的 `citationIds` 是否也能落到 `sources[].id`。
- 输出 citation diagnostics，便于联调时查看引用覆盖率、断链率和 quote 命中率。

因此，前端点击引用编号时，展示的是后端保存的真实来源片段，而不是模型随口生成的“参考资料”。

## 5. 模型 Provider 与 Prompt 编排

当前真实模型 Provider 是蓝心兼容接口。后端通过环境变量或本地密钥文件读取 Provider 配置，包括 base url、模型名、超时时间和重试次数。

模型调用由 Provider 层统一封装，Agent 编排层只关心“某个模块需要生成 JSON”。每个模块都有对应的 prompt 和输出契约，后端要求模型返回结构化 JSON，再对输出做解析和清洗。

如果启用严格 Provider 模式，模型调用失败会直接返回错误，不再退回 mock 结果。这符合当前项目“只保留真实后端链路”的要求，也避免演示时误以为已经联通真实模型。

模型调用的日志会写入结果 `_meta`，包括 provider、model、taskType、输入输出长度、延迟、状态和是否 fallback。这些信息主要用于诊断，不作为页面核心展示字段。

## 6. AgentResult 归一化与持久化

前后端之间的核心契约是 `AgentResult`。后端最终会把各阶段产物合并为统一结构，至少包含主题、摘要、阶段日志、来源、笔记、引用、思维导图和复习评估。

归一化层会处理几类问题：

- 补齐缺失的顶层字段，保证前端不会因为字段不存在而白屏。
- 兼容模型或 Prompt 中可能出现的字段别名，例如 `source_refs`、`node_id`、`question_type` 等。
- 规范思维导图节点和边，确保前端能按 `nodes` 和 `edges` 渲染。
- 检查引用关系，确保 note、citation、review question 指向的 source 存在。
- 生成稳定的 result id，用于后续刷新、RAG 查询和继续问答。

每次生成完成后，后端会把 `result.json` 和 `chunks.json` 写入运行目录。`result.json` 用于结果刷新和页面恢复，`chunks.json` 用于 RAG 查询和 M7 继续问答。运行目录属于可再生成产物，不应提交到代码仓库。

## 7. 查询、问答与校验接口

后端除了首次生成，还提供几个联调和二次使用接口。

`GET /api/agent/result/{result_id}` 会按 id 读取已保存的 `AgentResult`，前端结果页可用它刷新当前结果。

`POST /api/agent/validate` 会检查传入结果是否符合前端契约，返回字段完整性、来源数量、笔记数量、引用数量、题目数量和 valid 状态，适合联调时快速判断后端输出是否可被页面消费。

`POST /api/rag/query` 会基于 result id 或 chunks 路径进行来源召回，返回相关 chunk。它用于验证 RAG 证据链，也可以支撑结果页的“来源检索”调试能力。

`POST /api/agent/chat` 是 M7 继续问答入口。用户在已有结果基础上追问时，后端会读取保存的 result 和 chunks，先召回相关来源，再调用模型生成回答，并返回使用到的引用。

文档中提到的 `POST /api/agent/edit` 目前属于设计中的后续能力，当前 FastAPI 路由尚未实现。现阶段已生成结果的“AI 改写、补充、压缩、同步导图”等能力应标记为未落地，不应作为已完成联调能力展示。

## 8. 运行配置与安全边界

后端通过 `.env` 控制监听地址、端口、运行目录、允许读取的输入根目录、CORS、Provider 和模型配置。APK 或手机访问电脑后端时，后端需要监听 `0.0.0.0:8000`，前端运行时配置填写电脑局域网地址或 Android 模拟器的 `10.0.2.2`。

安全边界主要包括：

- 上传文件只保存到后端运行目录。
- 通过 `filePath` 读取本机文件时，路径必须位于 `BACKEND_ALLOWED_INPUT_ROOT` 下。
- 真实 API Key 保存在本地 `.env` 或密钥文件中，不进入仓库和文档。
- 运行产物、上传文件、生成结果、日志和 APK 都不作为源码提交。
- CORS 可以在演示阶段配置为 `*`，便于 APK 和浏览器联调；正式部署时应收紧来源。

## 9. 当前限制与后续扩展

当前后端已经覆盖真实生成、文件上传、引用 grounding、结果刷新、契约校验、RAG 查询和继续问答。主要限制是：

- `/api/agent/edit` 仍未实现，二次 AI 改写目前不能作为已完成能力。
- 真实模型调用耗时受资料长度和蓝心接口状态影响，复杂文档可能需要较长等待。
- 旧版 DOC 转换依赖 Windows 本机 Word 环境，跨平台稳定性弱于 DOCX。
- 中文检索效果依赖分词和 query 构造，联调时建议同时用原文关键词和英文/缩写关键词验证。
- 当前持久化使用本地文件系统，适合原型和演示；如果后续多人使用，需要接入数据库、任务队列和异步状态查询。

后续可以扩展的方向包括：异步任务进度、SSE 流式状态、结果版本管理、AI 编辑接口、用户级结果存储、Provider 多模型切换、检索质量评估面板和更细粒度的引用审计。
